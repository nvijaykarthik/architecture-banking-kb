> ## 1. Precise definition
> Kubernetes (K8s) is an open-source container orchestration platform originally developed by Google that automates the deployment, scaling, and management of containerized applications (CNCF). It is specified through 18 key resources (Pods, Services, Deployments, StatefulSets, etc.) and relies on 4 core primitives: the API server, etcd (cluster state), the scheduler, and the controller manager.
>
> ## 2. Why it exists (problem it solves)
> Banks spent 15+ years on x86 VM fleets managed by hand-written runbooks. A change to a core banking service required weeks of manual patching and capacity planning. Kubernetes introduced declarative, versioned infrastructure: the bank's declared desired state (three replicas of the Payments API) is continuously reconciled by the controller, and any deviation is auto-healed. For disaster recovery, the same manifest files can be deployed across regions.
>
> ## 3. Core concepts & vocabulary
> | Term | Precise meaning |
> |------|-----------------|
> | Pod | The atomic unit of deployment: one or more containers sharing the same network namespace, storage mounts, and IPC; thinks in EC2 terms (no cloud-native storage by default). |
> | OKD / OKD on AWS / Anthos | Enterprise clusters with enhanced security, billing isolation, and auditability required for classified banking workloads.
> | Container Image | An immutable artifact (OCI image) containing the application code, runtime, and dependencies; signed, scanned, and stored in a private registry for banking. |
> | ConfigMap / Secret | ConfigMap for non-sensitive configuration; Secret for base64-encoded secrets, but encryption at rest or external secrets management is required for PCI. |
> | CNI (Container Network Interface) | Pluggable interface for network; critical for zero-trust segmentation and pod-to-socket policies. |
> | Service Mesh (Istio / Linkerd) | Adds mTLS, observability, and fine-grained traffic management between pods; not required but recommended for banking compliance. |
>

> ## 5. Variants, options & trade-offs
> | Variant | When to pick | When to avoid | Key trade-off axis |
> |---------|--------------|---------------|--------------------|
> | Standard Upstream K8s | Greenfields, cloud-native teams, CI/CD maturity | Regulated workloads < 3 years audit | Simplicity vs. security |
> | OKD / RKE2 / Rancher | Enterprise compliance, on-prem data residency | Fully managed KaaS | Cost vs. control |
> | KubeVirt (Kubernetes + VMs) | Legacy VMs that must stay in cluster | PCI-DSS scope extension | Migration risk vs. speed |
>
> ## 6. Relationships to sibling topics
> - **Serverless (C10-03):** Serverless runs *on* K8s. Knative is the K8s-native serverless layer; not all serverless workloads need K8s, but every on-prem bank serverless workload usually does.
> - **Zero Trust (C10-06):** K8s RBAC is account-level access; true Zero Trust requires CNI policies + mTLS and per-RBAC auth across pods, says CISA.
> - **API Economy (C10-05):** K8s is the runtime for API Gateway ingress (Istio, Kong, Traefik) that hosts public-facing banking APIs.
>
> ## 7. Banking / financial-services context 💳
> A Tier-1 European bank runs its high-frequency-trading container fleet on OKD across two countries. Each namespace is labeled with `data-residency: eu-central`, `criticality: tiers-1`, and `ciso-approved`. A CVE in a 10-year-old OpenSSL library in one supply-chain container triggers the security team's automated roll-out of a patched pod version (canary) with zero downtime via the UseCase:Example scenario.
>
> ## 8. Reference architecture / worked example
> **Problem:** A bank's core banking platform runs on bare-metal x86; patching a kernel to address a Spectre variant requires a 48-hour maintenance window and manual restore.
>
> **Decision:** Migrate to OKD with immutable infrastructure (brownfield VMs become pods); apply a CI/CD pipeline that builds container images, runs static analysis, signs them with a private key, and deploys via GitOps (ArgoCD).

> ## 9. Maturity & adoption signals
> - **Adopt when:** > 30% of workload is container-native; on-prem or hybrid cloud strategy; compliance requires full control over runtime.
> - **Anti-signals (don't adopt yet):** < 3 years of ops experience; single monolith; latency < 10 ms; unstable network partitions.
> - **Common failure modes:** etcd backup/restore failure ("etcd-o-crashes" = fatal); ingress controller misconfiguration; privileged pod creation via cluster-admin.
>
> ## 10. Common confusions — the "don't mix" list
> | Often confused | Real distinction |
> |----------------|------------------|
> | Pod vs VM | Pod is an application unit; VM is a host/hardware. |
> | Kubernetes vs Docker | Docker is a container runtime; Kubernetes is an orchestrator for Docker and others. |
> | Helm vs Kustomize | Helm is template-based; Kustomize is overlay-based. Both manage YAML manifests.
>
> ## 11. Tools & standards to know
> - **Standards/Frameworks:** CNCF Spectrum and Kubernetes Security Whitepaper; SANS GCIH; CISA Kubernetes Hardening Guidance; PCI-DSS v4.0 (containers, images, runtime).
> - **Common tooling:** kubeadm, kind, K3s (lightweight), Rancher, New Relic, Datadog Container, ForgeOps Deepfence, OPA/Gatekeeper.
> - **Mandatory reading:** "Kubernetes: Up and Running" by Kelsey Hightower et al.; "Cloud-Native Go" by Kelsey Hightower.

> ## 14. Summary (1 paragraph)
> Kubernetes is the universal container orchestrator that decouples banking workloads from hardware and gives the enterprise a versionable, auto-healing, multi-cloud runtime. It is powerful but assumes operational maturity; for banks without a 24/7 SRE culture, the alternative is a managed Kubernetes service (EKS, AKS, GKE) that trades control for speed.
